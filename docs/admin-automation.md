# Админ панел и автоматично получаване на данни

Актуализирано: 23.09.2026 г. Работещата версия е Laravel със защитен React админ екран. Оригиналният интерфейс е използван от `legacy-react/src/pages/AdminPage.tsx`; работещият вариант е `legacy-react/src/admin/LaravelAdminPage.tsx`. Не използва frontend login gate, Supabase browser ключове или localStorage за конфигурациите.

## Адреси

| Екран | Път |
| --- | --- |
| Оригиналното оперативно табло и петте раздела | `/admin` |
| Връзки, график, грешки, история | `/admin/integrations` |
| Подготовка за Skroutz | `/admin/skroutz` |
| Всички входящи заявки и история на разговорите | `/admin/inbox` |
| Получен каталог от JAR | `/admin/supplier-catalog` |
| Документи, фактури и поръчки към JAR | `/admin/external-documents` |
| Разширени бизнес модули | `/admin/operations` |

Всички тези екрани и техните JSON маршрути изискват сървърна сесия с роля `admin`. Външните ключове се пазят криптирано чрез `APP_KEY` и не се връщат към браузъра. Празно поле за ключ запазва предишната стойност. При смяна на акаунта импортният курсор се изчиства. Не генерирайте нов `APP_KEY` за база с вече запазени ключове.

## Какво работи автоматично

| Раздел | Реално поведение | Какво е нужно |
| --- | --- | --- |
| Табло | Броячи от базата, обновяване на видимия екран всяка минута | Няма външен ключ |
| Заявки за ремонт | Формата създава заявка, клиент, сервизна поръчка и разговор. Промяната на статуса в оригиналния екран обновява сервизната поръчка | Физическият ремонт и предаването се отбелязват от служител |
| Контактни запитвания | Последните 100 разговора, прочетено/непрочетено; цялата история е във входящата кутия | Mail OAuth или активирани бизнес канали |
| Доверие и продажби | Запазени са оригиналните указания; Google отзиви се получават като чернови | Google Business Profile OAuth и одобрен API достъп |
| AI ценообразуване | Калкулатор по формули, сървърно записване/редактиране/архивиране, автоматично използване на актуални оферти за съответния SKU | Данни за себестойност, реални комисиони, доставка и разрешен ценови feed |
| JAR каталог | Пълен импорт веднъж дневно; цени и наличности на 15 минути | JAR акаунт с разрешен API и потвърдена валута |
| JAR документи | Поръчки, документи и фактури за последните 30 дни, повторна проверка на статуса | Същият JAR достъп |
| Валутни курсове | ЕЦБ веднъж дневно; остарял или невалиден XML се отказва | Няма API ключ |
| Анализи | Часово преизчисляване; оферти над 7 дни и демонстрационни записи не влияят на анализа | Работещ планировчик |
| Skroutz | Конфигурации, проверка за попълнени полета, XML и JSON преглед, приемане на webhook и потвърждение чрез Orders API | Активира се по-късно с търговски token и адрес на магазина |

„AI ценообразуване“ е запазено като име на оригиналния раздел. Няма обучен прогнозен модел или доказани данни за търсене. Оценките за търсене и конкуренция са ръчни допускания. Калкулаторът работи в EUR; себестойност и доставка са без възстановим ДДС, продажните цени са с ДДС. Сравнението с местната продажба използва стандартна ставка 20%. Данъчният режим и действителните комисиони трябва да съответстват на конкретния бизнес.

Разширеният стар ценови модул запазва съществуващите полета `base_price_bgn` и `exchange_rate_to_bgn`; записването от EUR анализатора използва фиксирания коефициент 1.95583. Това не преименува историческите стойности в базата на EUR.

## Необходими връзки

### JAR Computers

В „Интеграции“ попълнете JAR потребител, парола и валутата, потвърдена от доставчика. Използва се Basic Authentication само през HTTPS към `api.jarcomputers.com`. Реализирани са `products`, `products_short`, `orders`, `documents`, `invoices`, включително страниците на каталога. Не се правят поръчки към доставчика.

Цените се пазят в подадения вид; API документацията не е достатъчна за автоматично заключение дали всяка цена е с ДДС. Текстът за наличност при JAR е отделен от реалния склад в Благоевград. Фактура от доставчик не създава клиентско плащане. Проверявайте `synced_at`: липсващи от нов каталог артикули не се изтриват автоматично.

[Официална JAR API документация](https://api.jarcomputers.com/)

### Служебна поща

Поддържат се Gmail / Google Workspace и Microsoft 365 / Outlook. Администраторът на пощата създава OAuth приложение и предоставя Client ID, Client Secret, Refresh Token и адрес на служебната кутия. Разрешения: Gmail `gmail.readonly`; Microsoft delegated `Mail.Read` и `offline_access`. Самото интерактивно OAuth свързване се извършва при доставчика; в този панел се запазват получените данни за достъп.

Първото четене взима последните 7 дни от Inbox, следващите — от запазения курсор с петминутно застъпване. Идентификаторите предотвратяват повторни съобщения. Четат се текстът и подателят, без прикачени файлове. Писмата не се изпращат, изтриват или маркират като прочетени в доставчика. Microsoft refresh token се обновява криптирано при ротация. За друг пощенски доставчик е нужен допълнителен адаптер.

[Gmail API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) · [Microsoft Graph](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0)

### Конкурентни оферти

Търговски Skroutz акаунт и Products API управляват вашите продукти; това не е достъп до всички конкурентни цени. Нужен е разрешен източник на тези оферти. В `INTEGRATION_FEED_HOSTS` се задават точните разрешени домейни, разделени със запетая. В панела се въвеждат HTTPS URL и евентуален Bearer token. Пренасочвания не се следват.

Договор за JSON формата (илюстрация, не реална оферта):

```json
{"offers":[{"id":"external-offer-id","sku":"YOUR-SKU","market":"GR","source_key":"authorized-source","price":750.00,"currency":"EUR","includes_vat":true,"collected_at":"2026-09-23T09:00:00Z","url":"https://merchant.example/product","title":"Product name","availability":"In stock"}]}
```

Създайте съответните SKU, пазар и източник в разширения ценови модул. Валутата трябва да съвпада с пазара. Импортът е по идентификатор на оферта и източник; непълна или несъответстваща партида се отказва изцяло. Това е обновяване на подадените оферти, а не заличаване на всички липсващи от feed-а. Неподновени оферти отпадат от анализа след 7 дни.

### Google отзиви и други канали

Google Business Profile изисква одобрен API достъп, OAuth разрешение `business.manage`, Account ID и Location ID на собствения обект. Кодът използва само четене; новите отзиви се записват непубликувани за преглед. Съществуващите статични отзиви и сервизни цени на публичния сайт са отделно съдържание и не се подменят от този импорт.

WhatsApp, Messenger и Viber използват съществуващите webhook адаптери и сървърни настройки от `config/communications.php`; вижте `docs/publish-checklist.md`. Не са предоставени реални бизнес акаунти. Куриерски и банкови интеграции не са добавени: нужни са избран доставчик, договор, идентификатори на пратките и източник за потвърдени плащания.

[Google Business Profile](https://developers.google.com/my-business/content/review-data) · [ЕЦБ — курсове](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html) · [Ставки ДДС в ЕС](https://europa.eu/youreurope/business/finance-and-tax/vat/vat-rules-rates/index_en.htm)

## Подготовка за Skroutz

1. Създайте продукт/PC конфигурация от анализатора или от „Конфигурации“. Собствените компоненти се описват с CPU, GPU, RAM, SSD, дънна платка, захранване и кутия. Налични са оригиналните 10 стартови PC шаблона и запис на собствени шаблони. Стартовите цени са обозначени като примерни и не са живи оферти; шаблоните не са продаваем склад.
2. От „Skroutz“ попълнете стабилен SKU, име, публични HTTPS продуктова страница и снимка, категория, производител, MPN, EAN, описание, цена в EUR с ДДС, приложима ставка, количество и срок за доставка. За собствена сглобка потвърдете изискванията за идентификаторите със Skroutz.
3. Черновите могат да са непълни. При анализ от работния панел първо попълнете URL, дата до 14 дни и confidence поне 6/10 на benchmark, потвърдете данъчната основа и маркирайте „Одобрено за тест“. Сървърът изисква положителна печалба, минимален марж и достатъчна оценка. Промяна на анализа отменя ревизията и одобрението за износ. За Skroutz цената трябва да съвпада с одобрения анализ за Гърция. Изтекла ревизия се изключва от следващия износ. Одобряването на публикацията изисква всички продуктови полета. Само одобрени конфигурации и публикации влизат в XML; нулевата наличност се изключва. JSON прегледът включва `enabled: false` за нулев запас и цена в евроцентове. Прегледът не изпраща заявки към Products API.
4. Проверете XML с официалния валидатор. Техническата локална проверка не гарантира приемане на конкретната категория от Skroutz. Продуктовите страници трябва действително да съществуват и да показват същите данни — този проект засега е сервизен сайт, не пълен онлайн магазин.
5. По-късно запазете съществуващия Merchants token в „Интеграции“. Не създавайте нов token без нужда: Skroutz допуска един активен ключ и новият обезсилва стария. Регистрирайте HTTPS `/webhooks/skroutz` на домейна на магазина.
6. Включете `SKROUTZ_FEED_ENABLED=true` едва когато каталогът е готов. Подайте `/feeds/skroutz.xml` в Merchants. Feed и webhook приемат официалните IP диапазони от `config/skroutz.php`; обновявайте ги при промяна от Skroutz. Задайте точните доверени proxy адреси в `TRUSTED_PROXIES`, ако има reverse proxy.

Webhook съхранява код на задача, след което прочита поръчката през автентикирания Orders API. Не се доверява на клиентски имена, цени или статуси в самото входящо събитие. Идемпотентният импорт запазва външната поръчка отделно; това не означава получено плащане. Няма автоматично приемане/отказване на поръчки, купуване, изтегляне на товарителници или публикуване на цени. При неуспех историята показва грешка и webhook може да се повтори от Merchants.

[XML спецификация](https://developer.skroutz.gr/products/xml_feed/) · [Products API](https://developer.skroutz.gr/products/api/) · [Orders API](https://developer.skroutz.gr/smart_cart/orders_api/) · [Webhook](https://developer.skroutz.gr/smart_cart/orders_webhook/)

## Стартиране и публикуване

```powershell
.\setup-local.cmd
.\run-app.cmd
.\run-automation.cmd
```

`run-automation.cmd` пуска скрити локални процеси за scheduler, API queue и стандартната опашка. Спиране: `run-automation.cmd -Stop`. След промени по PHP кода рестартирайте тези процеси. Логовете са в `storage/logs/automation-*.log`. Промените по React админа изискват `npm run build:admin`; пълният `npm run build` изгражда и двата frontend пакета.

При ново инсталиране извън Windows:

```sh
composer install
npm ci
npm --prefix legacy-react ci
php artisan migrate --force
npm run build
```

На сървър са нужни PHP/Laravel, база данни, HTTPS и отделни процеси:

```sh
php artisan queue:work integrations --queue=integrations --sleep=2 --tries=1 --timeout=900
php artisan queue:work database --queue=default --sleep=2 --tries=3 --timeout=60
```

За споделен cPanel използвайте отделния [пакет и инструкции](cpanel-upload.md) с 15-минутни задачи. Следващата конфигурация е за сървър с постоянни worker процеси: Cron всяка минута изпълнява `php /absolute/project/path/artisan schedule:run`. Наблюдавайте процесите със Supervisor или услугата на хостинга. Timeout на API worker е 900 секунди, а `retry_after` е 960. За cPanel без постоянни процеси е нужна отделна конфигурация на bounded queue workers; качването само на статичен ZIP не стартира тези автоматизации. Document root трябва да е Laravel `public`, `APP_DEBUG=false`, а локалният демонстрационен администратор не трябва да се използва на продукция.

За свързване на исторически заявки: `php artisan business:reconcile`. Ръчно планиране на конкретен активиран източник: `php artisan integrations:dispatch --provider=jar`. След публикация: `php artisan queue:restart`, рестарт на integration worker и `php artisan optimize:clear` / конфигурационен cache според хостинга.

Ако Windows PHP няма CA bundle, използвайте актуалния [официален Mozilla bundle от curl](https://curl.se/docs/caextract.html) и задайте абсолютния път в `INTEGRATION_CA_BUNDLE`. HTTPS проверката остава включена. Локалният изтеглен bundle е в игнорираната папка `tools/downloads` и не е зависимост за нормално конфигуриран Linux сървър.
